--------------------------------------------------------------------------------
STEP 1 — CHECK DEPENDENCIES
--------------------------------------------------------------------------------

vitest is already in the root package.json (v4.1.9). Check for a DOM library:

  npm ls jsdom happy-dom

If neither is present, install one:

  npm install --save-dev jsdom

Angular's @angular/build:unit-test builder auto-detects happy-dom first,
then falls back to jsdom.

--------------------------------------------------------------------------------
STEP 2 — CREATE vitest.config.ts
--------------------------------------------------------------------------------

Create the file: core-libs/core/vitest.config.ts

This carries over the settings from karma.conf.js (coverage thresholds,
reporters, JUnit output path, etc.).

--- vitest.config.ts -----------------------------------------------------------

import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    environment: 'jsdom',
    setupFiles: [],
    coverage: {
      provider: 'v8',
      reportsDirectory: '../../coverage/core',
      thresholds: {
        statements: 90,
        lines: 90,
        branches: 80,
        functions: 90,
      },
    },
    reporters: ['default', 'junit'],
    outputFile: {
      junit: '../../unit-tests-reports/unit-test-core.xml',
    },
    globals: false,
  },
});

--------------------------------------------------------------------------------

Then wire it up in project.json:

  "test": {
    "executor": "@angular/build:unit-test",
    "options": {
      "tsConfig": "core-libs/core/tsconfig.spec.json",
      "runnerConfig": "core-libs/core/vitest.config.ts"
    }
  }

--------------------------------------------------------------------------------
STEP 3 — UPDATE src/test.ts (setup file)
--------------------------------------------------------------------------------

The current src/test.ts sets up the Angular TestBed. It is safe to reuse as
a Vitest setupFile. However, make two changes:

1. Remove the top comment referencing karma.conf.js (line 7):
   DELETE: "// This file is required by karma.conf.js and loads recursively..."

2. If you use fakeAsync / flush / waitForAsync in tests, add the zone.js
   Vitest patch as the FIRST import:

   import 'zone.js/plugins/vitest-patch';

   The Angular guide recommends migrating these to native async + Vitest fake
   timers eventually, but the patch is the safe short-term option.

The TestBed configuration (BrowserTestingModule, ZoneChangeDetectionModule,
destroyAfterEach: false) carries over unchanged.

--------------------------------------------------------------------------------
STEP 4 — RUN THE JASMINE-TO-VITEST REFACTOR SCHEMATIC
--------------------------------------------------------------------------------

This is the key automated step. It converts Jasmine API calls to Vitest
equivalents across all spec files in the library:

  ng g @schematics/angular:refactor-jasmine-vitest --project=core

Useful flags:
  --add-imports   Add explicit "import { vi } from 'vitest'" to each file
  --verbose       Print every file changed
  --include <path> Target a specific file or subdirectory only

Conversions performed by the schematic:
  +---------------------------------+---------------------------+
  | Jasmine                         | Vitest                    |
  +---------------------------------+---------------------------+
  | spyOn(obj, 'method')            | vi.spyOn(obj, 'method')   |
  | jasmine.createSpy('name')       | vi.fn()                   |
  | jasmine.objectContaining({...}) | expect.objectContaining() |
  | jasmine.arrayContaining([...])  | expect.arrayContaining()  |
  | jasmine.any(Type)               | expect.any(Type)          |
  | fit(...)                        | it.only(...)              |
  | fdescribe(...)                  | describe.only(...)        |
  | xit(...)                        | it.skip(...)              |
  | xdescribe(...)                  | describe.skip(...)        |
  +---------------------------------+---------------------------+

--------------------------------------------------------------------------------
STEP 5 — MANUAL FIXES NOT COVERED BY THE SCHEMATIC
--------------------------------------------------------------------------------

Review all spec files for these patterns that need manual migration:

  jasmine.clock()
    → vi.useFakeTimers() / vi.useRealTimers()

  jasmine.clock().install() / jasmine.clock().uninstall()
    → beforeEach(() => vi.useFakeTimers())
      afterEach(() => vi.useRealTimers())

  jasmine.clock().tick(ms)
    → vi.advanceTimersByTime(ms)

  Custom Jasmine matchers (jasmine.addMatchers / jasmine.addAsyncMatchers)
    → Vitest custom matchers via expect.extend({})

  jasmine-marbles (hot/cold/getTestScheduler)
    → jasmine-marbles is Jasmine-specific and has no drop-in Vitest equivalent.
      Options:
        a) @hirez_io/observer-spy (recommended for simple observable testing)
        b) rxjs/testing TestScheduler directly (more verbose but framework-agnostic)
      This is the most significant manual effort in this library.

  throwError() matcher
    → toThrow() / toThrowError() (Vitest uses the same name, verify syntax)

--------------------------------------------------------------------------------
STEP 6 — REMOVE KARMA ARTIFACTS
--------------------------------------------------------------------------------

Files to delete (once tests pass):
  core-libs/core/karma.conf.js

If src/test.ts is now only used as a Vitest setupFile and has been cleaned up,
keep it. Its new role is just TestBed initialization, not Karma bootstrap.

Packages to uninstall — ONLY after ALL libraries in the monorepo are migrated
(other core-libs likely still use Karma):

  npm uninstall karma karma-chrome-launcher karma-coverage \
    karma-jasmine karma-jasmine-html-reporter karma-junit-reporter \
    jasmine-core jasmine-marbles

--------------------------------------------------------------------------------
STEP 7 — RUN TESTS AND VERIFY
--------------------------------------------------------------------------------

  nx run core:test

Check:
  - All tests pass
  - Coverage thresholds are met (90% statements/lines/functions, 80% branches)
  - JUnit XML is generated at: unit-tests-reports/unit-test-core.xml
  - Coverage report is generated at: coverage/core/

For CI (see ci-scripts/unit-tests.sh), ensure the output paths and flags
match what the script expects.

--------------------------------------------------------------------------------
GOTCHAS SPECIFIC TO THIS PROJECT
--------------------------------------------------------------------------------

1. patch-object-define-property
   The custom testing utility imported in src/test.ts patches
   Object.defineProperty to allow spying on frozen/non-configurable properties.
   This should work fine with Vitest, but verify it does not use any
   Jasmine internals (e.g., jasmine.getEnv()).

2. jasmine-marbles (most impactful)
   This library is in the root devDependencies and is used for RxJS marble
   testing. It is tightly coupled to Jasmine. All marble tests will need
   manual rewriting — see Step 5 above.

3. destroyAfterEach: false
   This TestBed teardown option carries over unchanged to Vitest.

4. Random test order disabled (karma: random: false)
   Vitest runs tests in file order by default. Add to vitest.config.ts if
   you need to enforce sequence:
     test: { sequence: { shuffle: false } }

5. zone.js + fakeAsync
   fakeAsync and flush are zone.js APIs. They continue to work with Vitest
   via the 'zone.js/plugins/vitest-patch' import (see Step 3). Long-term,
   the Angular team recommends migrating these to native async patterns.

6. Coverage provider
   The karma.conf.js used Istanbul (karma-coverage). Vitest supports both
   'v8' and 'istanbul'. Use 'istanbul' in vitest.config.ts if you want
   identical coverage numbers during transition:
     npm install --save-dev @vitest/coverage-istanbul
     coverage: { provider: 'istanbul' }
