# Internationalization (i18n)

## Rule

NEVER hardcode user-facing strings in templates. Use the `cxTranslate` pipe with a translation key:

```html
{{ 'myFeature.myLabel' | cxTranslate }}
{{ 'myFeature.greeting' | cxTranslate: { name: user.name } }}
```

Hardcoded strings can't be translated and break the moment a second language is enabled. There is no compile-time error — the regression is silent.

## The resource shape

Translation resources nest **three levels deep under the language**:

```
lang → chunk → namespace → keys
```

A translation key like `myFeature.myLabel` splits into a **namespace** (`myFeature`, the first dot-separated segment) and a **key** (`myLabel`). At runtime Spartacus resolves the chunk that owns the namespace and looks up `resources[lang][chunk][namespace][key]`. Register resources at exactly this depth — a missing level makes the key render as its bracketed fallback (`[myFeature.myLabel]`) with no compile-time error.

## Registering translations (eager)

Feature modules register translations via `provideConfig`. The simplest form ships everything eagerly with the root bundle. Nest chunk, then namespace, then keys:

```typescript
export const myTranslations = {
  myFeatureChunk: {     // chunk
    myFeature: {        // namespace (first segment of the key `myFeature.myLabel`)
      myLabel: 'My Label',
      greeting: 'Hello, {{name}}!',
    },
  },
};

export const myTranslationChunks = {
  myFeatureChunk: ['myFeature'], // chunk name → list of namespaces it contains
};

provideConfig({
  i18n: {
    resources: { en: myTranslations },
    chunks: myTranslationChunks,
  },
})
```

`chunks` maps each **chunk name** to the list of **namespaces** it contains. Chunk and namespace are separate levels — this example gives them different names to keep that distinction visible. In practice a feature often names them the same, so you'll frequently see the two levels repeat one word (`myFeature.myFeature`).

Spartacus core groups several namespaces under one chunk — e.g. the `product` chunk holds the `productDetails`, `addToCart`, `productList`, … namespaces:

```typescript
// chunk config
{ product: ['productDetails', 'addToCart', /* … */] }

// resource shape it implies
resources.en.product.productDetails.title    // key 'productDetails.title'
resources.en.product.addToCart.addToCart     // key 'addToCart.addToCart'
```

With eager registration the resources are bundled into the root JS, which is fine for a few small dictionaries.

## Lazy-loaded translations

For larger dictionaries or per-feature translations, configure a backend `loader` so chunks load on demand. The `loader` returns a Promise of the chunk's resources (shaped `namespace → keys`), and a dynamic `import()` lets the bundler code-split each translation file:

```typescript
provideConfig({
  i18n: {
    backend: {
      loader: (lng, chunk) =>
        import(`../assets/i18n-assets/${lng}/${chunk}.json`),
    },
    chunks: myTranslationChunks,
    fallbackLang: 'en',
  },
})
```

Spartacus's `TranslationService` invokes the loader on demand, so a chunk is imported only when a key from one of its namespaces is first rendered. Prefer `backend.loader` over `backend.loadPath` for translations bundled with your app — it's more performant, especially under SSR. `loadPath` (an HTTP path with `{{lng}}`/`{{ns}}` placeholders) is recommended only for loading translations from an external server.

## Plurals

Don't branch in component logic to choose singular vs. plural wording. i18next picks the plural form from the `count` option using the language's CLDR rules. Provide a base key (singular) plus a `_other` variant, and pass `count`:

```typescript
// translations — namespace `storeFinder`
storesFound: '{{ count }} store found',
storesFound_other: '{{ count }} stores found',
```

```html
{{ 'storeFinder.storesFound' | cxTranslate: { count: stores.length } }}
```

i18next resolves `storesFound_other` when `count !== 1`. Some languages need more categories (`_zero`, `_few`, `_many`); the full set of suffixes and rules is in the [i18next plurals spec](https://www.i18next.com/translation-function/plurals).

## Anti-pattern

```html
<!-- ❌ Hardcoded user-facing strings — cannot be translated, no chunk loading -->
<button>Add to wishlist</button>
<h2>Recently viewed products</h2>
```

```html
<!-- ✅ cxTranslate pipe + translation chunk -->
<button>{{ 'wishlist.addAction' | cxTranslate }}</button>
<h2>{{ 'recentlyViewed.title' | cxTranslate }}</h2>
```

```typescript
// ❌ Two levels — the namespace level is missing
resources: { en: { myFeature: { myLabel: 'My Label' } } }

// ✅ Three levels: lang → chunk → namespace → keys
resources: { en: { myFeature: { myFeature: { myLabel: 'My Label' } } } }
```

## Debugging translations

If a key renders in brackets (`[myFeature.myLabel]`) or shows the fallback, check the resource nesting first — it must be `lang → chunk → namespace → key`. Then turn on i18n debug logging to see every lookup, which chunks load, and missing keys in the console:

```typescript
provideConfig({ i18n: { debug: true } }) // never enable in production
```

To test a single key resolves at runtime:

```typescript
inject(TranslationService).translate('myFeature.myLabel').subscribe(console.log);
```

## Source reference (in `node_modules/@spartacus/*`)

- `TranslatePipe` (`cxTranslate`), `TranslationService`, `I18nConfig` from `@spartacus/core`.
- Default translation chunks ship from `@spartacus/assets` and `@spartacus/*/assets`. Their `en/index.ts` files show the `lang → chunk → namespace → keys` shape (e.g. `common.json` holds the `common`, `spinner`, `navigation`, … namespaces).
